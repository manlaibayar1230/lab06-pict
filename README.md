# Хэсэг A: Category-Partition — `POST /transfer`

## Олон алдааны давуу эрэмбэ

Нэг хүсэлтэд хэд хэдэн алдаа зэрэг байвал **from → to → amount** дарааллаар, тус бүрийн дотор **байхгүй → төлөв** (NO_FROM → FROZEN, NO_TO → SAME_ACCOUNT), amount-д **BAD_AMOUNT → INSUFFICIENT → LIMIT** гэж эхний таарсан алдааг буцаана гэж тогтоов: байхгүй дансны царцаасан эсэхийг шалгах боломжгүй, үлдэгдэл/лимитийн шалгалт нь хоёр данс тодорхой болж ханш хөрвүүлсний дараа л утга учиртай, үлдэгдэл хүрэлцэхгүй нь лимитээс илүү "хатуу" (өдөр солигдоход ч засагдахгүй) хязгаар тул түрүүлж шалгана.

Бүрэн эрэмбэ: `NO_FROM > FROZEN > NO_TO > SAME_ACCOUNT > BAD_AMOUNT > INSUFFICIENT > LIMIT`

## A1. Сонголт ба төлөөлөх утгууд (A2-ын хязгаарлалттай)

| Параметр / орчин | Сонголт (category) | Төлөөлөх утга (choice) | Хязгаарлалт |
|---|---|---|---|
| `from` | Дансны оршин байх ба төлөв | **Valid** — байгаа, царцаагдаагүй данс (`A-100`, үлдэгдэл 1 000 000₮) | `[property fromOK]` |
|  |  | **Frozen** — байгаа ч царцаагдсан (`A-200`) | `[ERROR]` |
|  |  | **Missing** — байхгүй ID (`A-999`) | `[ERROR]` |
| `to` | Хүлээн авах данс | **Valid** — байгаа, `from`-оос өөр (`B-300`) | `[property toOK]` |
|  |  | **Missing** — байхгүй ID (`B-999`) | `[ERROR]` |
|  |  | **SameAsFrom** — `to == from` | `[ERROR]` |
| `amount` (хөрвүүлсний дараах дүнгээр) | Тэмдэг ба хэмжээ | **Negative** — `-5000` | `[ERROR]` |
|  |  | **Zero** — `0` | `[ERROR]` |
|  |  | **Normal** — `0 < дүн ≤ min(үлдэгдэл, лимитийн үлдэгдэл)` (`50 000₮`) | `[property amountOK]` |
|  |  | **EqualBalance** — яг үлдэгдэлтэй тэнцүү (`1 000 000₮`, лимит хүрэлцэнэ) | `[SINGLE]` |
|  |  | **OverBalance** — үлдэгдлээс 1 нэгжээр их (`1 000 001₮`) | `[ERROR]` |
|  |  | **OverLimit** — үлдэгдэлд багтана, өдрийн лимитийн үлдэгдлээс их | `[ERROR]` |

|  |  | **Different** — `USD` → ханшаар MNT болгоно | `[property convert]` |
| *Далд орчин:* өдрийн лимит | Өнөөдөр лимит хэр дүүрсэн бэ | **Unused** — өнөөдөр шилжүүлэг хийгээгүй (лимит 5 000 000₮ бүтэн) | — |
|  |  | **Partial** — 4 500 000₮ ашигласан (500 000₮ үлдсэн) | — |
|  |  | **Exhausted** — лимит бүрэн дүүрсэн (0₮ үлдсэн) | `[ERROR]` |

Бусад далд орчин: ханшийн утга (тогтмол гэж үзэв), дансны үлдэгдэл (amount-ийн утгууд үлдэгдэлтэй харьцангуй тодорхойлогдсон тул тусад нь category гаргаагүй).

## A2. Хязгаарлалтын үндэслэл

- **`[ERROR]`** — `from`=Frozen/Missing, `to`=Missing/SameAsFrom, `amount`=Negative/Zero/OverBalance/OverLimit, лимит=Exhausted: тус бүр нэг тодорхой ERROR кодыг үүсгэх бөгөөд бусад утгатай хослуулах нь шинэ мэдээлэл өгөхгүй (эхний алдаа бусдаа нууна — error masking), тиймээс тус бүрийг ганц удаа, бусад нь хүчинтэй үед шалгана.
- **`[SINGLE]`** — `amount`=EqualBalance: хилийн (boundary) утга бөгөөд амжилттай болох ёстой ч бүх currency/лимит хослолтой давтах шаардлагагүй тул нэг удаа шалгана.
- **`[property]`/`[IF]`** — Normal/EqualBalance amount нь зөвхөн `[if fromOK and toOK]` үед утга учиртай (үгүй бол үлдэгдлийг тооцох данс байхгүй); `Different` currency `[property convert]` нь amount-ийн утгууд хөрвүүлсний дараах дүнгээр сонгогдохыг шаардана; лимит Partial нь `[if amountOK]` — зөвхөн хэвийн дүнтэй үед лимитийн үлдэгдэл үр дүнд нөлөөлнө.

## Тестийн хүрээний тоо: N → M

- **Бүрэн олонлог (хязгаарлалтгүй):** from 3 × to 3 × amount 6 × currency 2 × лимит 3 = **324**
- **Хязгаарлалтын дараа:**
  - `[ERROR]` утга бүр 1 фрейм: 2 (from) + 2 (to) + 4 (amount) + 1 (лимит) = **9**
  - `[SINGLE]` утга: EqualBalance = **1**
  - Үлдсэн хүчинтэй хослол: from Valid(1) × to Valid(1) × amount Normal(1) × currency (2) × лимит Unused/Partial (2) = **4**
  - Нийт: 9 + 1 + 4 = **14**

**324 → 14**

# Хэсэг B: PICT — pairwise covering array

Бүх командыг Git Bash-д `export MSYS_NO_PATHCONV=1`-ийн дараа ажиллуулсан. `/r` (санамсаргүй seed) ашиглаагүй.

## B1. Браузерын жишээ (`browser.model`)

```bash
pict browser.model | tee results/browser-2way.txt
pict browser.model /o:3 > results/browser-3way.txt
tail -n +2 results/browser-2way.txt | wc -l    # 10
tail -n +2 results/browser-3way.txt | wc -l    # 20
```

| Хувилбар | Мөрийн тоо | Онолын доод хязгаар | Бүрэн олонлог |
|---|---|---|---|
| 2-way (`results/browser-2way.txt`) | **10** | 3 × 3 = 9 (Content×Cookies хосууд) | 3·3·2·2·2·2 = 144 |
| 3-way (`results/browser-3way.txt`) | **20** | 3 × 3 × 2 = 18 | 144 |

**Яагаад 9 биш 10 вэ (greedy):** Лекц дээр Content×Cookies-ийн 9 хосыг 9 мөрөнд тавиад үлдсэн 4 хоёртын параметрийг гараар тааруулж 9 мөрөнд багтаасан. PICT нь greedy алгоритм — мөр бүрийг "одоогоор хамгийн олон хамрагдаагүй хосыг хамрах" байдлаар нэг нэгээр нь сонгодог ба өмнөх сонголтоо буцааж засдаггүй тул хамгийн цөөн (оновчтой) массивыг заавал олдоггүй; энд 1 мөр илүү гарсан. Энэ нь хурдан, тогтвортой (seed-гүй үед үргэлж ижил) үр дүнгийн төлөө төлсөн жижиг үнэ юм.

**3-way:** 20 мөр нь бүрэн олонлогийн 144-ийн ≈14% бөгөөд аливаа 3 параметрийн бүх утгын гурвалыг хамарна; 2-way-ээс 2 дахин олон ч бүрэн тестээс 7 дахин цөөн.

**Ажиглалт:**

- **Хязгаарлалтгүй (`transfer-nc`)** — 19 мөрийн нэг нь ч happy path биш, 16 мөрөнд 2–4 алдаа зэрэг орсон (жишээ: `Frozen Missing OverBalance Same Exhausted`). Ийм мөр эхний алдаагаа (давуу эрэмбээр FROZEN) буцаагаад бусдыг нууна (error masking) тул `Missing to`, `OverBalance`, `Exhausted`-ийн зан төлөвийг огт шалгадаггүй — олон алдаатай мөр юуг шалгаж байгаа нь тодорхойгүй. Мөн 4 мөр бодит байдалд боломжгүй буюу хоёрдмол (жишээ: `OverLimit` + `Unused` — 1 000 000₮ үлдэгдэлд багтах ч 5 000 000₮ лимитээс их дүн байхгүй).
- **Хязгаарлалттай (`transfer`)** — мөр бүрт хамгийн ихдээ 1 алдаа, боломжгүй мөргүй. Гэхдээ 2 happy path мөр хоёулаа `EqualBalance` (хил) бөгөөд энгийн `Valid Valid Normal … Unused/Partial` happy path гарсангүй — `Normal` нь алдаатай мөрүүдэд "дүүргэгч" утгаар хангалттай хосолсон тул greedy алгоритм тусдаа мөр үүсгээгүй. Мөрийн тоо 19 → 21 болж өссөн нь хязгаарлалт нь хэд хэдэн хосыг нэг мөрөнд нийлүүлэх боломжийг хаасантай холбоотой.
- **Сөрөг утгатай (`transfer-neg`)** — `~` нь "нэг мөрөнд хамгийн ихдээ нэг сөрөг утга" гэдгийг PICT өөрөө хангадаг тул A2-ын `[ERROR]` хязгаарлалт (`IF [From] <> "Valid" THEN …`) хэрэггүй болсон. Харин PICT сөрөг утга бүрийг бүх эерэг утгатай хосолж, эерэг утгуудыг хооронд нь бүрэн хосолсон байхыг шаарддаг тул 26 мөр, 5 happy path (`Normal` ба `EqualBalance`, хоёр валют) гарсан. **`[IF/property]` хязгаарлалт хэрэгтэй хэвээр**: `OverLimit → Partial`, `EqualBalance → Unused`-г хасвал `~OverLimit` + `Unused` гэх мэт боломжгүй мөр дахин гарна — `~` нь зөвхөн алдааны семантикийг (ERROR) орлодог, утгын бодит боломжит байдлыг (property) орлохгүй.

## Дүгнэлт

Category-partition арга нь тодорхойлолтыг сонголт, утга, хязгаарлалт болгон задлахыг шаарддаг бөгөөд энэ лабын хамгийн их бодол шаардсан алхам нь A2 — аль утга `[ERROR]`, аль нь `[SINGLE]`, аль нь `[IF/property]` болохыг шийдэх, ялангуяа "өдрийн лимит хэр дүүрсэн бэ" гэсэн далд орчны сонголтыг олж, `OverLimit` нь зөвхөн лимит хэсэгчлэн ашиглагдсан үед л боломжтой гэдгийг ойлгох байлаа. Тодорхойлолтод олон алдааны эрэмбэ байхгүй тул `NO_FROM > FROZEN > NO_TO > SAME_ACCOUNT > BAD_AMOUNT > INSUFFICIENT > LIMIT` гэж өөрөө тогтоосон нь давхар нөхцөлийн спецификаци болон PICT-ийн олон алдаатай мөрийн oracle-ын үндэс болсон. Хязгаарлалт нь бүрэн олонлогийг 324-өөс 14 фрейм болгож багасгасан бөгөөд A3-ын 18 спецификацид бүх фреймийг хамруулж, давхар нөхцөл ба хөрвүүлэлтийн тохиолдлыг нэмсэн. PICT-ийн браузерын жишээнд 2-way 10 мөр гарч лекцийн гараар олсон 9-өөс нэгээр илүү байсан нь greedy алгоритм хамгийн цөөнийг баталгаажуулдаггүйг харуулсан, харин 3-way 20 мөр нь 144-ийн бүрэн олонлогоос 7 дахин цөөн. Шилжүүлгийн модельд хязгаарлалтгүй хувилбар 19 мөртэй ч нэг ч happy path гаргаагүй, 16 мөрөнд 2–4 алдаа зэрэг орж error masking үүсгэсэн. A2-ын хязгаарлалт нэмэхэд мөр бүрт хамгийн ихдээ 1 алдаа болж утга учиртай болсон ч энгийн happy path алга болсон тул PICT-ийн гаралтад сохроор итгэх биш уншиж шалгах шаардлагатайг ойлгосон. `~` сөрөг утга нь `[ERROR]`-ын хязгаарлалтыг орлож 26 мөр, 5 happy path өгсөн ч `[IF/property]` хязгаарлалт хэрэгтэй хэвээр үлдсэн. Иймээс гар арга алдааны семантик ба oracle-ыг илүү сайн барьдаг бол PICT нь хосын хамралтыг автоматаар баталгаажуулдаг — хамгийн сайн нь category-partition-оор семантикаа тодорхойлоод, түүнийгээ PICT-ийн `~` ба `IF`-ээр кодчилж хамралтаа автоматжуулах хосолмол арга юм.
